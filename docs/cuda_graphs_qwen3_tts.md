# CUDA Graphs と Qwen3-TTS の高速化：技術解説

> 対象: Jetson AGX Thor 上の Qwen3-TTS（1.7B CustomVoice）を、`faster-qwen3-tts` で高速化した件
> 作成日: 2026-10-18
> 凡例: **【実測】** = このプロジェクトで測った値 / **【一般】** = 一般的な技術知識 / **【推定】** = 筋は通るが、未検証の解釈

---

## 0. 結論（先に）

| 問い | 答え |
|---|---|
| 何が遅かったのか | GPU の計算ではなく、**CPU が GPU に小さな命令を大量に発行する処理**（Python と PyTorch のオーバーヘッド）が律速だった |
| CUDA Graph とは | GPU への一連の命令を**一度だけ記録**し、以降は**1 回の命令で再生**する仕組み |
| なぜ速くなるのか | 命令の発行回数が、1 ステップあたり約 500 回から 1 回に減り、GPU の待ち時間（隙間）が消える |
| 代償 | **形状と記憶領域を固定**する必要がある。柔軟性、デバッグ性、版への依存、同時実行に制約が出る |
| 今回の効果 | 1 フレームあたり約 90〜100ms から 43〜53ms（約 2 倍）。RTF 1.1〜1.3 から 0.53〜0.66【実測】 |

---

## 1. 用語の整理：「動的グラフ」は 3 つの意味で使われる

「動的」という言葉は、文脈で別のものを指します。混同しやすいので、先に分けます。

| 用語 | 意味 | 今回の関係 |
|---|---|---|
| **動的計算グラフ**（define-by-run / eager 実行） | PyTorch の既定の動作。Python のコードを 1 行ずつ実行し、**そのたびに演算を GPU に発行**する | 遅かった原因の本体 |
| **動的形状**（dynamic shapes） | 実行のたびに**テンソルの大きさが変わる**こと。例: 生成のたびに伸びる KV キャッシュ | CUDA Graph が苦手とするもの |
| **静的グラフ**（graph capture） | 演算の並びを**一度記録して固定**し、再生する方式。CUDA Graph がこれ | 今回の解決策 |

つまり、**「動的に作る（柔軟だが遅い）」から「静的に記録する（固い）が速い」**への切り替えが、今回の本質です。

## 2. 何が遅かったのか：自己回帰デコードの構造

### 2.1 Qwen3-TTS の 1 フレーム分の処理

Qwen3-TTS は、音声を約 12 フレーム/秒（12Hz コーデック）で、1 フレームずつ生成します。

```text
1 フレームの生成
 ├─ Talker（28 層の Transformer）      → 最初のコードブック 1 つを出す
 └─ Code Predictor（5 層）× 15 ステップ → 残りのコードブック 15 個を順に出す
```

`faster-qwen3-tts` の README によると、**1 ステップに小さな GPU 呼び出し（カーネル）が約 500 回**あり、GPU は計算よりも、次の呼び出しを待つ時間のほうが長い、とされています【一般（README の記述）】。

### 2.2 なぜ「小さな呼び出し」が問題になるのか

バッチサイズ 1 のデコードでは、1 つ 1 つの演算が小さくなります（行列とベクトルの積など）。GPU 側の実行は数 µs〜数十 µs で終わりますが、CPU 側には次のコストがかかります【一般】。

```text
Python のインタプリタ → PyTorch のディスパッチャ → CUDA ドライバ → GPU へ発行
   （演算 1 つにつき、数 µs〜数十 µs 程度が目安）
```

1 つの Transformer 層には、正規化、QKV 射影、RoPE、注意、出力射影、残差、MLP（3 つの射影と活性化）など、**十数個の演算**があります。28 層なら 400〜600 回で、README の約 500 回と整合します【推定】。

### 2.3 タイムラインで見る

```text
[eager 実行：CPU が律速]
CPU : |発行|  |発行|  |発行|  |発行|  |発行|  ...   ← 1 つずつ発行（Python が遅い）
GPU :    |実行|  |実行|  |実行|  |実行|  ...        ← 実行が短く、発行を待つ（隙間）
              ↑隙間 = GPU が遊んでいる時間

[CUDA Graph：記録を再生]
CPU : |発行（1 回）|                                  ← グラフ全体を 1 回で発行
GPU :    |実行|実行|実行|実行|実行|実行|...|          ← 隙間なく連続して実行
```

### 2.4 このプロジェクトでの裏づけ【実測】

| 観測 | 値 | 読み取り |
|---|---|---|
| `tegrastats` の CPU | **1 コアだけが 95〜100%（2601MHz）**、他は 0〜10% | Python のメインスレッドが張り付いている（シングルスレッドの CPU 律速） |
| `nvidia-smi` の GPU 使用率 | 合成中に **45〜50% で安定** | GPU が約半分の時間、待たされている |
| バッチ実験（1.7B） | batch=4 でも時間は batch=1 の **1.21 倍** | 4 倍の仕事が 1.2 倍で終わる = 計算量ではなく呼び出し回数が律速 |
| 0.6B への変更 | 1.7B より**速くならない**（3.33 秒 対 2.92 秒） | モデルを小さくしても、呼び出し回数は同じ |

この 4 つが、すべて「CPU の発行律速」を指しています。

## 3. CUDA Graph の仕組み

### 3.1 基本の流れ

```python
g = torch.cuda.CUDAGraph()
static_in = torch.zeros(...)                  # 固定の入力バッファ

# ウォームアップ（別ストリームで数回走らせ、初期化を済ませる）
# 記録（capture）
with torch.cuda.graph(g):
    static_out = model(static_in)             # この間に発行された演算が「記録」される

# 再生（replay）
for step in ...:
    static_in.copy_(new_input)                # 入力を固定バッファに「書き込む」
    g.replay()                                # 記録した全演算を 1 回で発行
    result = static_out.clone()               # 出力は固定バッファから読む
```

### 3.2 記録される内容

グラフには、**カーネルの並び、その引数（メモリのアドレスを含む）、依存関係**が保存されます【一般】。再生時には、同じアドレスに対して、同じ演算が実行されます。

### 3.3 なぜ速くなるのか（3 つの効果）

| 効果 | 内容 |
|---|---|
| ① **CPU の発行コストの削減** | 約 500 回の発行が、1 回（`cudaGraphLaunch`）になる。Python と PyTorch のディスパッチャを通らない |
| ② **GPU の隙間の解消** | カーネル間の待ち（発行を待つ時間）がなくなり、GPU が連続して実行できる |
| ③ **ドライバ側の最適化** | グラフ全体の依存関係が事前に分かるため、ドライバが起動処理を効率化できる【一般】 |

### 3.4 記録中に許されないこと【一般】

| 禁止事項 | 理由 |
|---|---|
| CPU との同期（`.item()`、`.cpu()`、テンソルの値の表示） | 記録中は演算が実行されないため、値が存在しない |
| 新しいメモリ確保（`cudaMalloc`） | アドレスが固定されるため。専用のメモリプール内で確保される |
| データに依存した分岐（`if tensor > 0:`） | 記録時の分岐が固定され、再生時に変わらない |
| 形状の変化 | 記録した形状のカーネルしか実行できない |

## 4. 「動的」をどう静的に収めるか：faster-qwen3-tts の工夫

### 4.1 問題：KV キャッシュが伸びる

標準の Hugging Face の `DynamicCache` は、ステップごとに `torch.cat` で KV を**伸ばします**。

```text
step 1: KV 長 = 100
step 2: KV 長 = 101    ← 形状が変わる
step 3: KV 長 = 102
```

形状がステップごとに変わるので、1 つのグラフを再利用できません。

### 4.2 解決策：「値は動的、形状は静的」

README の説明（`Static KV cache`、`Padded attention`）から読み取れる設計です。

```text
・KV キャッシュを、最大長（max_seq_len）で最初に確保する（形状が固定）
・今の位置は、GPU 上のテンソルに持つ（位置の「値」だけが変わる）
・使っていない位置は、注意のマスクで隠す（padded attention）
・各ステップで、決まった位置に新しい KV を書き込む
```

位置の更新や書き込みを、**値がテンソルで与えられる演算**（`index_copy_` など）で行えば、形状は固定のまま、動的な値を扱えます【一般的な手法。faster-qwen3-tts の内部実装の細部は未確認】。

### 4.3 同じ工夫の副作用：パディング分の無駄

最大長が 2048 なら、実際の長さが 100 でも、注意は 2048 個分の領域に対して計算されます（マスクで隠すだけ）。

ただし【実測】では、`max_seq_len` を 2048 から 512 に変えても、速度に差がありませんでした（43〜44ms/フレームで同じ）。この長さ・このモデルでは、パディングの影響は小さいと言えます。

## 5. なぜ `torch.compile` は失敗したのか【実測】

同じ「グラフ化」でも、`torch.compile(mode="reduce-overhead")` を標準の生成ループに当てたところ、2 つの問題が出ました。

| 事象 | ログ | 原因 |
|---|---|---|
| ① 再コンパイルの連発 | `size mismatch at index 1. expected 2, actual 3`（`attention_mask`） | 生成のたびに形状が変わり、**コンパイル時に仮定した形状**（ガード）が外れる |
| ② 実行時エラー | `accessing tensor output of CUDAGraphs that has been overwritten by a subsequent run` | `DynamicCache` が `torch.cat` で**前のステップのグラフの出力**を保持しようとするが、その領域は**次の再生で上書き**される |

②が本質的な衝突です。CUDA Graph の出力バッファは、再生のたびに**同じ場所を再利用**します。「前の結果を後で参照する」書き方（動的キャッシュの `cat`）は、これと相性が悪いのです。

`faster-qwen3-tts` が成功した理由は、**グラフ化の前提（静的な KV、固定形状）を、モデルのコード側から作り直した**点にあります。コンパイラに任せるのではなく、設計から変えています。

## 6. 効果の大きさ【実測】

### 6.1 今回の結果

| 項目 | 素の実装 | CUDA Graph | 変化 |
|---|---|---|---|
| 1 フレームあたり | 約 90〜100ms | 43〜53ms | 約 2 倍 |
| RTF（処理時間 ÷ 音声の長さ） | 1.1〜1.3 | 0.53〜0.66 | |
| ストリーミング最初の音（chunk_size=4） | — | 286ms | |
| `gpu_mem_allocated` | 4.21GB | 4.37GB | +0.16GB |
| 起動時の `warmup` | — | 2.2 秒 | |

### 6.2 なぜ 10 倍にならないのか

README の Orin（0.6B）では、1 ステップが 330ms から 54ms（約 6 倍）でした。Thor では約 2 倍です。**DGX Spark の README の値（約 1.9 倍）と近い**【実測と README の比較】。

| 要因 | 解釈【推定】 |
|---|---|
| Orin の素の実装が極端に遅い | Orin の CPU が遅く、発行律速がより深刻。取り除ける無駄が大きい |
| Thor は CPU が速い | 素の実装の時点で、すでに無駄が小さい。取り除ける分が少ない |
| 取り除けない部分が残る | GPU の実計算、メモリ帯域（重みの読み出し）、コーデックのデコード、サンプリング、CPU との同期（終了判定）など |

**アムダールの法則**の典型例です。ボトルネックの一部（発行オーバーヘッド）を消すと、残りの部分（計算とメモリ）が新しい上限になります。

### 6.3 注意：フレーム数の換算

ベンチのスクリプトでは、1 秒を 12.5 フレームとして `ms/frame` を計算しました。README の記述（`chunk_size=8` が 667ms 分）では、1 フレームは約 83ms（12 フレーム/秒）です。したがって、`ms/frame` の値は約 4% 小さく出ています。**RTF（処理時間 ÷ 音声の長さ）は、この換算の影響を受けません**。比較には RTF を使ってください。

### 6.4 検証の方法（次にやるなら）

効果の理由を、数字で確かめる方法です。

```bash
# 合成中に、CPU と GPU の使用率を見る
tegrastats --interval 200
nvidia-smi --query-gpu=utilization.gpu --format=csv -l 1
```

予測【推定】: CUDA Graph の後は、**1 コアの 100% 張り付きが下がり、GPU 使用率が上がる**（素の実装では 45〜50%）。結果が逆なら、この解釈を見直します。

さらに詳しくは、`nsys profile`（Nsight Systems）で、**カーネル間の隙間**が消えているかを、タイムラインで確認できます。

## 7. デメリットと制約

### 7.1 一覧

| # | 制約 | 内容 | このプロジェクトでの影響 |
|---|---|---|---|
| 1 | **形状の固定** | 最大長を決めて確保し、パディングで埋める。それを超える入力は扱えない | `max_seq_len`（既定 2048）と `max_new_tokens` で上限。短い応答の用途では問題なし |
| 2 | **メモリの追加消費** | 静的バッファとグラフ専用のメモリプールが常駐する。形状ごとに別のグラフを持つと増える | +0.16GB（小さい）【実測】 |
| 3 | **起動時間** | 記録（capture）のウォームアップが必要。`torch.compile` なら数十秒〜数分 | 2.2 秒【実測】。コンテナの起動時のみ |
| 4 | **柔軟性の低下** | 記録された演算の並びは固定。データに依存した分岐や、実行時の構造変更ができない | 生成の終了判定は、グラフの外（CPU 側）で行う必要がある |
| 5 | **CPU との同期が残る** | 終了判定（EOS トークン）やチャンクの取り出しで、定期的に同期が必要 | `chunk_size` が小さいと同期が増え、RTF が悪化する（2 で 0.80、8 で 0.59）【実測】 |
| 6 | **デバッグの難しさ** | 記録中のエラーが分かりにくい。入力バッファの更新漏れが、**エラーなしで誤った結果**を返す危険がある | 出力の音を、素の実装と聞き比べる検証が必要 |
| 7 | **版への依存** | `transformers` の内部クラス（`StaticLayer` など）の API 変更で壊れる | 実際に発生した。`transformers==5.15.1` に固定した【実測】 |
| 8 | **ビット単位では一致しない** | 静的キャッシュでは、選ばれる注意カーネルや、演算の順序が変わる。bf16 では結果がわずかに違う | README にも記載。聞いて確認する |
| 9 | **同時実行の制約** | グラフは固定のバッファを使うため、同じグラフを並行して再生できない。リクエストは 1 つずつ | サーバでロックを使う。単一ユーザの用途では許容 |
| 10 | **GPU が律速の処理では効果が小さい** | カーネルが大きい処理（大きなバッチ、長い系列）では、発行コストの比率が低い | 今回は該当せず（短い発話、バッチ 1） |

### 7.2 特に注意すべき点

**① 暗黙の失敗（#6）**

静的バッファへの入力の書き込みを忘れると、**直前の入力のまま再生し続けます**。エラーは出ません。検証では、**複数の異なる入力を連続して処理し、毎回の出力が入力に対応していること**を確認します。

**② 割り込み（barge-in）との相性（#4、#9）**

ストリーミングの途中で再生を止めても、サーバ側の生成が走り続け、ロックを保持し続けると、次のリクエストが待たされます。**接続の切断を検知して生成を止める**実装が、Phase 2 で必要です。

**③ 版の更新（#7）**

`transformers`、`qwen-tts-hf`、`faster-qwen3-tts`、PyTorch のいずれを更新しても、動かなくなる可能性があります。**更新のたびに、`load_check.py` と `bench_faster.py` で再確認**してください。

## 8. 他の選択肢との比較

| 手法 | 仕組み | 長所 | 短所 |
|---|---|---|---|
| eager（素の実装） | 1 演算ずつ発行 | 柔軟、デバッグしやすい | 発行律速（今回の問題） |
| **手動の CUDA Graph**（今回） | 静的キャッシュ + 手動で記録 | 発行コストを消せる。`torch.compile` に依存しない | モデルのコードの作り込みが必要。版依存 |
| `torch.compile` | 演算の融合 + 自動のグラフ化 | 自動で最適化できる（形状が固定なら） | 動的形状で再コンパイルや失敗。Thor では `max_autotune` 系が使えない（SM 数の警告）【実測】 |
| 専用エンジン（vLLM、TensorRT-LLM など） | 最適化されたランタイム | 最も速くなりうる | 対応モデルが限られる。導入コストが大きい |
| 小さい／別のモデル | 呼び出し回数が違う構造 | 構造的に速い | 品質の評価からやり直し。NeMo の Magpie や AivisSpeech などが候補 |

## 9. このプロジェクトでの運用指針

| 項目 | 方針 |
|---|---|
| 構成の固定 | `transformers==5.15.1`、`tokenizers==0.22.2`、`huggingface-hub==1.33.0`、`qwen-tts-hf==0.1.1.post1`、`faster-qwen3-tts==0.5.4`。**5.16 以降は `MimiConfig` から `rope_theta` が消え、シムが読めない**ため使えない |
| 上限の設定 | `max_seq_len=2048`（既定）、`max_new_tokens` は用途に合わせて制限（例: 512 で約 40 秒分）。暴走の防止 |
| 同時実行 | サーバ側のロックで 1 リクエストずつ |
| 起動 | `warmup` のあと、通常の合成も 1 回走らせる。`start_period` に余裕を持つ |
| 検証 | 素の実装（旧イメージ）と、同じ文の音を聞き比べる。複数の異なる入力で、出力が入力に対応しているか確認 |
| 更新時 | 依存を更新したら、`load_check.py` → `bench_faster.py` の順に再確認し、**RTF の悪化がないか**を見る |
| 予備 | 旧イメージ `vms/tts:dev`（素の実装）を残す |

## 10. 用語集

| 用語 | 意味 |
|---|---|
| カーネル | GPU 上で実行される 1 つの関数（行列積など） |
| カーネルの発行（launch） | CPU が GPU に「このカーネルを実行せよ」と命令すること |
| 発行律速（launch-bound） | GPU の実行より、CPU の発行が遅いことで全体が決まる状態 |
| 自己回帰（autoregressive） | 直前の出力を入力にして、1 つずつ生成する方式 |
| KV キャッシュ | 注意（Attention）で使う、過去の Key と Value の保存領域 |
| RTF | Real-Time Factor。処理時間 ÷ 音声の長さ（小さいほど速い）。**このドキュメントでは 1 未満が実時間より速い** |
| TTFA | Time To First Audio。最初の音声が出るまでの時間 |
| capture / replay | グラフの記録 / 再生 |

> 注意：`faster-qwen3-tts` の README では、RTF を**逆数**（音声の長さ ÷ 処理時間、大きいほど速い）で表記しています。比較するときは換算してください。
